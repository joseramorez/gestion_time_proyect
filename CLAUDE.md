# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Scope: desktop only

Flutter app (`gestion_time_proyect`, a time-management app) targeting **Windows, macOS and Linux only**. Android, iOS and web were deliberately removed — do not re-add them or run `flutter create` for those platforms. To regenerate a desktop platform folder: `flutter create --platforms=windows,macos,linux .`

## Commands

```
flutter pub get
flutter run -d windows        # or macos / linux (must run on that host OS)
flutter analyze               # lints: flutter_lints via analysis_options.yaml
flutter test                  # all tests
flutter test test/domain/usecases_test.dart --plain-name "<test name>"   # single test
flutter build windows         # or macos / linux
./build_windows.ps1 [-Verify] [-Zip]   # release build via tool/flutter_env.ps1 (root script); -Zip -> dist/my-jira-work-time-windows.zip
./build_macos.sh [--verify] [--zip]    # same on a Mac (must run on macOS; unsigned .app); both honor DRY_RUN=1
```

Dart SDK `^3.12.0`.

Human-facing docs (Spanish): `README.md` (features, setup), `docs/architecture.md` (layers, dependency rules, recipes), `docs/ui-kit.md` (tokens, limits per view, components) and `docs/jira.md` (Jira setup, flow, troubleshooting). Keep them in sync when behaviour changes.

## Architecture (layered — read `docs/architecture.md`)

`lib/` is split into `config/` (`router/`, `theme/`), `core/` (`utils/`, `services/`), `domain/` (`entities/`, `errors/`, `repositories/`, `usecases/`), `data/` (`datasources/`, `models/`, `repository/`), `presentation/` (`viewModels/`, `screens/` + `screens/dialogs/`) and `widgets/` (UI kit: `buttons/ inputs/ chips/ layout/ dialogs/`).

**Dependency rules are enforced by `test/architecture_test.dart` — do not bypass them:**
- `domain` is pure Dart: no Flutter, no packages, no import of any other layer, no `dart:io`/`dart:ui`.
- `data` never imports `presentation`/`widgets`/Flutter widgets. `presentation/viewModels` never imports `widgets`, `screens` or `material.dart`. `widgets` never imports `presentation`/`data`/`domain/usecases`. `config`/`core` don't depend on `presentation`/`widgets`.
- Inside `lib/`, **all internal imports are `package:gestion_time_proyect/...`** (never relative). `test/` may use relative imports for `test/support`.
- Known deviation: `JiraController` (viewModel) uses the Jira datasources directly — there is no `JiraRepository` yet.
- There is deliberately no `blocs/` or `providers/` folder: state is `ChangeNotifier` view models.

Where things go: a business rule → a use case in `domain/usecases` (pure, takes `now` as a parameter, tested without a DB); storage change → `data/`; screen/dialog → `presentation/screens`; UI state → `presentation/viewModels`; reusable visual piece → `widgets/<type>/` + export in `widgets/widgets.dart`; any color/size/limit → `config/theme`.

### UI kit (`config/theme` + `widgets`) — use it, don't bypass it

Screens import `config/theme/theme.dart` and `widgets/widgets.dart`. `test/core/ui_kit_test.dart` fails if `Icons.*` is used outside `config/theme/app_icons.dart`, `IconButton` outside `widgets/buttons/`, `TextField`/`TextFormField`/`InputDecoration` outside `widgets/inputs/` (and `config/theme`), or `ThemeData`/`Color(0x…)` outside `config/theme`.
- Icons are named by function (`AppIcons.cutToJira`). Buttons: `AppIconButton` (requires `tooltip`; sizes compact 30 / regular 36 / large 40; variants plain/tonal/filled — it sets tonal/filled colors explicitly because an `AppBar` overrides the icon color of filled buttons). Inputs: `AppTextField` (+ `.multiline`/`.secret`/`.digits`). Labels: `AppChip` (tones neutral/accent/success/danger/brand; one line; max width `ChipLimits`), `JiraStatusChip` maps the Jira status *category* to a tone. Layout: `AppPanel`, `AppSectionLabel`, `AppEmptyState`, `AppDialogBody`.
- Per-view limits live in `config/theme/app_limits.dart` (`WindowLimits`, `ChipLimits`, `FieldLimits`, `DialogLimits`, `CompactLimits`, `TileLimits`). The tile row is `[play 40][clock ≤96][— status chip —][3 actions × 30]`; at the 360 px minimum window the chip slot is 87 px (min 84, asserted by a test). Adding a control to the tile shrinks that slot — the test will tell you.
- Window: MIN size is 360×242 (`WindowLimits.min`); the START size is a quarter of the screen (`WindowLimits.startFor(screen)` = half width × half height, never below min; `main.dart` reads the display from `WidgetsBinding.platformDispatcher.displays` and centers it); the compact view's window is 280×100 (outer size, includes the OS title bar).
- App icon is generated (`python tool/generate_icon.py`, needs Pillow) into `assets/icon/`, the Windows `.ico` and the macOS `AppIcon.appiconset`. Linux has no runner icon.
- AppBar: with 4 actions the title hides its text when it doesn't fit instead of overflowing. Re-check when adding an AppBar action.

### Domain and time model
- `Project` (entity, no serialization): time is `accumulatedMs` + `startedAtMs` (set while running); `elapsed()` derives the live value so timers survive restarts. Never store a ticking counter. Serialization is `data/models/project_model.dart` (`ProjectModel.toMap/fromMap`); Jira session JSON is `JiraSessionModel`.
- Use cases: `StartProject` (only one runs at a time; returns just the changed projects), `PauseProject`, `ClearProject`, `ApplyJiraCut` (subtract what was sent; keeps running if it was; less than measured → remainder kept, more → zero; `reset` → always zero), `PrepareWorklog` (1 min–24 h, our own guards; `started = now − duration`), `FindStaleJiraKeys`, `EvaluateGoal`, `SplitMinutes`.
- `ProjectsController` (viewModel) holds the list/preferences and persists every change at once through the `ProjectsRepository` contract; `ProjectsRepositoryImpl` wraps `AppDatabase` (SQLite via `sqflite_common_ffi`, file `gestion_time.db`). Tests use `AppDatabase.open(path: inMemoryDatabasePath)` or the in-memory `FakeProjectsRepository` (`test/support/fakes.dart`).
- DB is at v8 (v8 added `projects.time_since_ms`): `day_sent` (see Daily progress below; v7 dropped the old `work_intervals`/`day_cuts`) + `projects(jira_key, jira_logged_ms, jira_status, jira_status_category, jira_estimate_s, jira_remaining_s, jira_spent_s)` + `settings(key,value)` (`always_on_top`, `opacity`, `opacity_compact`, `confirm_close`, `jira_auto_sync`). `jira_logged_ms` = sent *by this app*; `jira_spent_s` = Jira's total for ALL users. Jira time-tracking NULL = "not reported" — never coerce to 0.

### Daily progress and optional daily cut
- The cut is never mandatory and never opens by itself; the ONLY block is per ticket (see "Carried-over" below). Progress = sum of the CURRENT stopwatches of all tickets (`DailyController.ticketsTotal`, live via the 1 s ticker); clearing a ticket or uploading with reset removes it. There is no history of intervals and no mandatory cut (v7 dropped `work_intervals`/`day_cuts`).
- "Uploaded today" = `day_sent(day, project_id FK cascade, seconds)` (`WorkLogRepository.sentOn(today)/addSent/deleteForProject`). It is shown apart (green segment/text in `DayProgressBar`), never added to the tickets' total, and is zero the next day (key = `dayKey(now)`; a 30 s timer reloads it on rollover). A per-ticket cut (`JiraController.logWork` -> `registerJiraCut` -> `onJiraSent` -> `DailyController.recordSent`) also counts.
- Cut dialog (`showDayCutDialog`, opened by the cloud button of `DayProgressBar`; dismissible): one row per ticket with >= 1 min snapshotted at open; Jira rows have **h / min** fields (no seconds, `SplitMinutes` truncates) and their own "Subir"; "Subir todos (n)" uploads the valid ones. `DailyController.upload/uploadAll(minutes, reset)` -> `post` (= `JiraController.postWorklog`, `started = now - duration`) -> on success `registerJiraCut(recordSent:false, reset)` then `addSent` (a bookkeeping failure never undoes the cut). One failing ticket doesn't stop the others; `sending` rejects re-entry.
- **Work day** (not upload day): each Jira row of the cut dialog has a day dropdown with exactly TWO scenarios: today and the "previous record" (`DailyController.previousDayFor` = the day the ticket's time comes from if known, possibly several days back; otherwise `previousWorkday(today)`, i.e. Friday on Mondays). Default = `suggestedDay`. **Jira only ever receives the TIME** (`started = now - duration`, same as the per-ticket cut): the day is purely internal bookkeeping. `upload(day:)`/`UploadRequest(project, minutes, day)` -> `addSent(day, ...)` records under that day (future days rejected), and only `day == today` feeds `sentToday`/the goal total (other days are shown as "para otros días").
- Carried-over time **blocks starting that ticket** (and only that one): `DailyController.isStartBlocked` (= not running && `carriesOlderTime`) -> `ProjectsController.canStart(project)` (injected in `main.dart`; a blocked `start` returns before pausing the running ticket) and `ProjectTile.startBlockedTooltip` disables play. Resolved by uploading all its time (reset) or Limpiar; pausing is always allowed and a running stopwatch is never stopped; < 1 min leftover doesn't count (can't be uploaded); the per-ticket cut button of such a ticket opens the day cut (`onCutDay`) so the time is booked on its work day. Warning: `Project.timeSinceMs` = instant the stopwatch left zero (set by `StartProject` from zero, kept on resume/partial cut, cleared by `ClearProject` and by `ApplyJiraCut` when nothing remains; NULL = unknown, e.g. data from before v8 — no warning). `carriesTimeBefore(today)` -> `DailyController.carriedOver` -> hint line in `DayProgressBar` + notice and default day in the cut dialog + a hint in the per-ticket `JiraCutDialog` (only reached for tickets without older time).
- **After a per-ticket cut of a RUNNING ticket** `showJiraCutDialog` asks (`showAfterCutDialog`: Detener / Reiniciar, not dismissible) whether to stop it or let it restart from zero; `ApplyJiraCut` itself still keeps a running stopwatch running. The day-cut dialog and the close flow do not ask.
- `reset` (checkbox, default on; also in the per-ticket `JiraCutDialog`, which has no seconds field either): `ApplyJiraCut(reset:true)` leaves the stopwatch at 0 (keeps running from 0 if it was running) while `jiraLoggedMs` only grows by what was uploaded.
- Status vs goal (`EvaluateGoal` -> `GoalStatus`): short (< minimum) / acceptable (minimum..goal) / met / over, compared in rounded minutes; only advisory. Compared total = uploaded today + what is about to be uploaded. Minimum = `AppEnv.dailyMinimum` (`DAILY_MIN_HOURS`, default 7 h, capped to goal).
- Goal: `AppEnv.dailyGoal` from `DAILY_HOURS` (compile-time `--dart-define-from-file`, decimals ok, invalid/<=0/>24 -> 8 h). `AppEnv` lives in `config/env` (not domain) because config may not import domain. Foreign keys need `PRAGMA foreign_keys = ON` (set in `onConfigure`).

### Windows and views
- `core/services/window_service.dart`: `WindowService` interface + `ManagedWindowService` (window_manager). UI code talks to the interface; tests use `FakeWindowService`.
- **Compact view** (pin icon): `ProjectsController.compactMode` (never persisted — the app always starts in the full view) switches `HomePage` to `CompactView`: only the running ticket's name + time + its own opacity slider, always on top, not resizable. **It only exists while a ticket is running**: `canUseCompactMode` is false otherwise, `setCompactMode(true)` is ignored, the pin button is disabled (tooltip explains why), and `CompactView` exits by itself if no ticket is running. **Exit must always be possible**: a visible corner button, double-click on the name/time, or Esc; `HomePage._exitCompact` flips the state in a `finally` and `ManagedWindowService` runs each native step separately, so a failing window call can never leave the UI trapped. It has its **own opacity** (`compactOpacity`, setting `opacity_compact`), separate from `opacity`; the slider applies to the window live via `onOpacity` and persists on release. Enter: flip the state first, then shrink the window; exit: grow the window first, then flip the state. The "Ventana" dialog also has both sliders and the always-on-top switch (the old pin behaviour).
- **The compact window sizes itself to its content** (`WindowLimits.compact` 280×140 is only the starting size): `CompactView` measures its natural height (via `OverflowBox` + `SizeChangedLayoutNotifier`, so it never raises an overflow error) and reports `onFit(content, client)`; `WindowService.fitCompact` computes `compactWindowHeight` = content + (outer − client), i.e. it subtracts the title bar/borders *of that machine* (they vary with display scaling — a fixed height overflowed by 2 px on one PC). It converges and is idempotent.
- **Close confirmation**: `CloseGuard` (wraps `HomePage`) keeps `WindowService.setPreventClose(true)` and listens to `closeRequests` (window_manager `onWindowClose`); `showCloseDialog` asks before `WindowService.close()` (destroy). Setting `confirm_close` (`ProjectsController.confirmClose`, default on, switch in the "Ventana" dialog); off + nothing running → closes without asking. With running tickets: pause, "upload" (`DailyController.pauseAndUploadRunning` → pauses, then `uploadAll` on Jira tickets with ≥ 1 min at their `suggestedDay`; any failure keeps the app open and shows the error) or leave running (time survives via `startedAtMs`). If the compact view is active it exits first (`beforePrompt`). Cmd+Q on macOS is not intercepted.
- **Jira auto-sync**: `JiraAutoSync` (viewModels; started in `main.dart`) ticks every `AppEnv.jiraAutoSyncInterval` (`JIRA_AUTO_SYNC_HOURS`, default 2 h, min 5 min, compile-time like the other `.env` keys) and runs `jira.sync` only if `ProjectsController.autoSyncJira` (setting `jira_auto_sync`, default on, switch + interval legend in the "Ventana" dialog) && signed in && not busy. No sync at launch; failures are left in the Jira state and retried next tick. `.env`, `.env.example` and `.env.development` carry the key.
- **List search/filter/sort**: `ProjectFilter` (domain value: query, statuses, origin, activity, onlyUploadable, onlyCarried, hideDone, sort; `hideDone` is ON by default and does not count as an active filter — showing finished tickets does — and never hides a finished ticket that is running or has ≥ 1 min of Jira time to upload; saved JSON is `v:2`, older saves get the new default) + pure `FilterProjects` (stable sort; accent/case-insensitive search; `noStatus` = 'Sin estado' for manual/unsynced; "uploadable" = Jira entry with ≥ 1 min; "carried" = `Project.carriesTimeBefore`). `ProjectsController.filter/setFilter/clearFilter/visibleProjects/hiddenCount/statusOptions`; ONLY `HomePage`'s list uses `visibleProjects` — `projects`, `running`, daily totals and the compact view still see everything. Saved as JSON in `settings.list_filter` (`ProjectFilterModel`, tolerant of bad data); the query is NOT saved and typing never writes. UI: `ListFilterBar` (one row: `AppTextField.search` + sort `PopupMenuButton` + filter `AppIconButton` with `Badge`) and `showListFilterDialog` (sort lives only in the bar menu to keep the dialog short).
- **Play prompt**: `ProjectTile._play` — for a Jira ticket in Backlog / Selected for Development (`ShouldOfferInProgress`, domain) with a signed-in session that `canWrite`, play first shows `showStartInProgressDialog` (Poner en curso / Solo iniciar / Cancelar). The stopwatch starts right away for both non-cancel choices; "Poner en curso" then runs `PickInProgressTransition` over `jira.transitionsFor` (prefers In Progress/En curso/En progreso among `indeterminate`; ambiguous → opens the status menu) and `changeStatus`. A failed transition only shows a snackbar — it never stops the timer. No session/permission → no prompt.
- **Jira status change**: the status chip (`JiraStatusChip(onTap:)`, tile + info dialog) opens `showJiraStatusMenu` (a dropdown `showMenu` anchored to the chip — pass the chip's own context via `Builder`; errors/success go to a snackbar, no dialog) → `JiraController.transitionsFor` (`GET /issue/{key}/transitions`) and `changeStatus` (`POST …/transitions`, scope `write:jira-work`). A Jira status is a *transition* of the project's workflow, not a free value. The local status/category is updated ONLY after Jira accepts (keeping the time-tracking fields, null ≠ 0), then a best-effort re-read; 400 = the transition needs required fields (not handled; tell the user to do it in Jira). Manual only — never automatic on start/pause. `showProjectInfo(..., jira:)` is optional; without it the info chip is not tappable.
- `showFittedDialog` (`widgets/dialogs`) — use it instead of `showDialog`: the window starts at its minimum size, so it measures the dialog and enlarges the window if needed (restored on close). Exception: the ticket info dialog never enlarges the window (only its buttons are fixed, the rest scrolls; truncated description + "Ver más"; in short windows the description goes right after the name).
- `RobustPaste` (`widgets/inputs`) overrides Ctrl+V with a retrying clipboard read (Windows can lock the clipboard briefly). Already applied inside `showFittedDialog`.

### Jira (OAuth 2.0 3LO, browser login)
- `data/datasources/jira_oauth.dart`: loopback server on fixed port 53682 (Atlassian needs the exact registered callback; ignores requests without the right `state`), token exchange/refresh. Atlassian requires `client_secret` (no PKCE for Cloud), so each user supplies the Client ID/Secret of their own OAuth app; never commit a shared secret. Credentials come from ONE of two places: (1) a `.env` (`JIRA_CLIENT_ID` + `JIRA_CLIENT_SECRET`, template `.env.example`, git-ignored) compiled in through `--dart-define-from-file=.env` (Flutter parses `.env` natively; no package) — `JiraController.hasBuildCredentials` is true only when BOTH are set; then they **win over stored ones**, the dialog hides the form and the "Credenciales" button, and stored credentials of a *different* Client ID are deleted together with their session on `load()`; `saveCredentials` is ignored. (2) Otherwise the dialog shows the form and saves to the OS secure store (a half-filled `.env` counts as "none"; its ID just pre-fills the form). `--dart-define-from-file` FAILS if the file is missing, so use `tool/flutter_env.ps1` / `tool/flutter_env.sh` (they add the flag only when `.env` exists; `DRY_RUN=1` prints the command). The secret is extractable from the compiled binary (verified). Never test a build with a dummy `.env` against the real app: it would wipe the user's stored credentials — use an in-memory `SecretStore`. Shell scripts must stay LF (`.gitattributes`). Secrets/tokens live in the OS secure store (`SecretStore`), never SQLite.
- `data/datasources/jira_api.dart`: `assignee = currentUser() AND statusCategory != Done`, paginated `search/jql`, ADF→text, `addWorklog` (ADF comment, `started` formatted by `jiraTimestamp`), `liveInfoFor` (`key in (...)` in chunks of 50, keys validated by regex, a 400 chunk is bisected to isolate a missing key).
- `JiraController`: imported issues (tasks and subtasks alike) become independent `projects` rows keyed by `jira_key`; re-sync updates name/description/link/status/time-tracking only and never touches measured time or deletes entries. The JQL excludes Done, so `sync` also refreshes status + time tracking of already-imported keys that stopped coming back (a failure there never aborts the import). Token refresh/401-retry-once is shared via `_withToken`; the refresh response may omit `scope`, so the previous one is preserved.
- Cut (`logWork(..., duration:)` + `presentation/screens/dialogs/jira_cut_dialog.dart`): editable summary (h/min — no seconds — + reset checkbox + comment). Needs scope `write:jira-work` (`JiraSession.canWrite`; old read-only sessions must re-login). Only on success it calls `registerJiraCut`, then re-reads the ticket (best effort) because Jira adjusts spent/remaining. A network error after the POST is ambiguous (possible duplicate) — the message tells the user to check Jira.
- The Jira dialog always has a **Cerrar** button (left of the primary action, enabled even while busy); rarely used actions (Credenciales, Cerrar sesión) live in the body, not the footer.

### Testing gotchas
- A test file that starts the OAuth loopback server must NOT contain any `testWidgets` (the widget binding intercepts real HTTP, even localhost → 30 s hang, port left busy). Each such file uses its own port (`JiraOAuth(port: …)`): `jira_test` 53690, `jira_cut_test` 53691, `jira_status_test` 53692. Files run in parallel.
- A `testWidgets` that starts a stopwatch leaves a periodic `Timer` (the controller's ticker): dispose the controller *inside* the test body, before the framework's pending-timer check (see `widgetTest` in `test/presentation/compact_view_test.dart`). Double-tap tests need a final `pump(1s)` for the gesture timers.
- Never wrap the whole compact view (or any area with buttons/sliders) in a `GestureDetector(onDoubleTap:)`: the double-tap recognizer waits ~300 ms for a second tap, delaying every tap on the children by that long (the exit button looked broken in tests and would feel laggy). Scope it to the text area only.
- When pumping a different theme in the same tree, `pumpAndSettle()` before measuring colors (the theme animates for 200 ms).

`windows/`, `macos/` and `linux/` are standard Flutter-generated native runners. They contain no app logic. Don't hand-edit `generated_plugin_registrant.*`, `GeneratedPluginRegistrant.swift` or `macos/Flutter/ephemeral/` — they are regenerated by `flutter pub get`/build. `.metadata` lists only the root, linux, macos and windows platforms; keep it in sync if platforms change.
